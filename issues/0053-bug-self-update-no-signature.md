# bug: self update に必須の署名検証と更新確認を追加する

- Created: 2026-10-26
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-self-update-signature
- Polished: {YYYY-MM-DD}

## 目的

`vss self update` が取得する成果物の署名を、バイナリに埋め込んだ信頼済み公開鍵で検証する。
署名、更新先バージョン、対象プラットフォームを確認してから展開し、検証失敗時には既存バイナリを変更しない。

HTTPS と同じ配布元のチェックサムだけでは、Release の書き込み権限を持つトークンなどによる成果物とチェックサムの同時差し替えを防げない。
配布先への書き込み権限だけを侵害されても、正規の署名鍵を使えなければ不正な成果物を適用できない構成にする。
署名鍵や署名可能な CI 自体の侵害は、検証コードだけでは防げないため、鍵の運用も対応範囲に含める。

## 現状

確認日: 2026-10-26。
確認対象: HEAD `d4d5ab6`（v0.22.0）と作業ツリー。
作業ツリーには CalVer `2026.10.0` への移行中の変更があるが、署名対応はない。
公開済み Releases と GitHub Environment の設定は未確認。

- `Cargo.toml` の `self_update` は 1.3.2 で、`signatures` と `checksums` feature が無効。
- `src/subcommand_self/update.rs` の `update` は、検証用公開鍵や追加の検証処理を設定せず、`no_confirm(true)` で更新する。
- `.github/workflows/release.yaml` は、アーカイブごとの `.sha256` と GitHub Artifact Attestations を生成する構成になっているが、zipsign による署名はない。
- `self update` は、そのチェックサムと attestation を検証していない。
- リリースワークフローでは、タグ名の検査、シェルへの安全な受け渡し、Actions のコミット SHA 固定、ジョブ単位の権限指定、全成果物のアップロード後の公開が実装済み。
- 成果物名は `vss_linux_amd64.tar.gz` などで、バージョンを含まない。
- `scripts/install.sh` と `scripts/install.ps1` は `.sha256` を照合するが、署名は検証しない。
- 以前の issue が指摘していた依存クレートは更新済み。署名対応とは分けて [0054](0054-update-vulnerable-dependencies.md) で管理する。

`self_update 1.3.2` の実装を確認したところ、zipsign の検証は展開前に行われ、アーカイブのファイル名を署名の context として照合する。
ただし、`signatures` feature を有効にしても、`verifying_keys` が空なら検証は無効のまま成功する。
また、`checksums` feature による GitHub asset digest の自動検証は、digest がない場合には省略される。
どちらも feature の有効化だけで必須検証を実現したと扱わない。

## 設計方針

### 1. 既存の更新クレートを維持して署名検証を必須にする

- `self_update` を維持し、`signatures` と `checksums` feature を有効にする。
- 本番用の信頼済み公開鍵を vss バイナリに埋め込み、`verifying_keys` に必ず設定する。
- 公開鍵の空集合、未署名、不正な署名、未知の鍵による署名はエラーにする。
- アーカイブを展開する前に署名とチェックサムを検証する。
- リリースごとの `.sha256` を必須の検証元とし、欠落、不正形式、不一致でも失敗させる。GitHub asset digest があれば検証する機能だけに依存しない。
- 検証後も、必要な `vss` / `vss.exe` 以外のファイルを配置せず、パストラバーサルやシンボリックリンクによる展開先外への書き込みを拒否する。
- 検証失敗時は既存バイナリを保持し、失敗理由を表示する。
- 署名なしへのフォールバックや、検証を省略するオプションは用意しない。

チェックサムは破損や配布ミスの検出にも使うが、署名の代替とはしない。
`axoupdater` への移行や、ダウンロードしたインストーラーの再実行だけでは、今回の署名検証要件を満たさないため採用しない。

### 2. 署名をバージョンと対象プラットフォームに結び付ける

正しく署名された過去の成果物を、別バージョンの成果物として再利用されることも拒否する。

- 第一候補は `vss_2026.10.0_linux_amd64.tar.gz` のような、バージョンと対象プラットフォームを含む正規アセット名とする。
- 選択したリリースのバージョンとターゲットから期待する名前を組み立て、その名前を署名 context として照合する。
- タグの `v` 接頭辞の正規化と、CalVer の比較規則を明示する。タグとビルドする `Cargo.toml` のバージョンの一致もリリース時に検査する。
- `self_update` の標準的なアセット検索に任せて、旧名、別バージョン、別ターゲットの成果物を誤選択しないようにする。
- バージョンなしの現在の名前を維持する必要がある場合は、更新先バージョン、ターゲット、ファイル名、SHA-256 を含む署名付きメタデータを別途検証する。名前を変えずに署名だけ追加する案では、この条件を満たしたと扱わない。
- 通常の更新では暗黙のダウングレードを拒否する。

アセット名を変更する場合は、両インストーラー、旧版の自己更新、利用案内への影響を検証する。
旧名の互換アセットが必要でも、新しい更新処理が未検証の互換アセットへフォールバックすることは許可しない。

### 3. リリース側の署名と鍵運用を整える

[0055](0055-bug-release-workflow-tag-injection.md) と連動して実装する。

- 処理順序を「ビルド → アーカイブ作成 → zipsign 署名 → 最終ファイルの SHA-256 と attestation 生成 → アップロード → 公開」にする。
- 署名後のファイルを変更せず、配布するファイルそのものにチェックサムと attestation を対応させる。
- `cargo build --locked` を使い、使用する署名ツールのバージョンも固定する。
- ビルドと署名を別ジョブにし、ビルドジョブには署名秘密鍵を渡さない。
- 秘密鍵はリポジトリに保存せず、保護された GitHub Environment の Secret などで管理する。
- Environment の承認、利用できるタグやブランチの制限、リリース対象コミットの承認方法を決める。タグの書式検査だけで信頼できるソースと判断しない。
- ワークフロー変更にレビューを要求し、署名ジョブに必要な権限だけを付ける。
- 鍵の管理者、Secret 名、バックアップ方法、通常の鍵更新手順、漏えい時の復旧手順を文書化する。
- 通常の鍵更新では、新旧鍵での二重署名と信頼済み公開鍵の移行期間を設ける。旧鍵が漏えいした場合、旧版クライアントからその鍵への信頼を自動で取り消せるとは想定しない。

本番用の公開鍵と Secret 名は管理者の決定待ち。
エージェントが本番用鍵を独断で生成または採用しない。

### 4. 更新確認と初回移行を整える

- 既定では現在と更新先のバージョン、対象成果物、検証結果を表示して確認を求める。
- 非対話環境では明示的な `--yes` を要求する。
- `--yes` が省略するのは確認操作だけとし、署名検証とチェックサム検証は省略しない。
- 未署名の旧リリースへの更新は、新しいクライアントでは安全側に失敗させる。
- 署名未対応の旧版には、初回更新時の署名検証を後から強制できないことを明記する。
- 最初の署名対応版を導入する際に、別経路で公開鍵やハッシュを照合できる手順を用意する。同じ Release にある未署名のチェックサムだけで、初回導入の真正性を保証したと説明しない。

### 今回の対象外と後続検討

- Artifact Attestations の生成は維持するが、更新時の必須検証は後続対応とする。この issue の初期実装では、必須の zipsign 検証とバージョンの対応付けを優先する。
- 将来 attestation を検証する場合は、ハッシュだけでなく期待するリポジトリとリリースワークフローも照合する。通常の自己更新に外部の `gh` / `cosign` CLI を必須にする構成は避ける。
- インストーラー自体の署名検証と初回導入の信頼確立は [0056](0056-bug-install-scripts-unverified.md) と連動する。アセット名変更への追従は今回の互換性確認に含む。
- パッケージマネージャー経由で導入したバイナリの自己更新制限は、uv の install receipt を参考に別途検討する。
- TUF などによる鍵失効、厳密な巻き戻し防止、古い更新情報を返し続ける攻撃への対策は別途検討する。初期実装だけでこれらすべてを防げるとは説明しない。

- `README.md` などの導入案内と `CHANGELOG.md`: 移行手順、動作変更、鍵運用の案内。

## 2026-10-26 のクライアント側の部分実装

- `stack/triage-01-signed-update` で現状を再確認した。署名なしの標準 `.update()` と `no_confirm(true)` が残っており、実装前の `cargo test --all --locked` は成功した。
- `self_update` の `signatures` / `checksums` を有効にし、メタデータ取得、ダウンロード、zipsign 検証の API を維持した。必須の SHA-256、厳密な成果物選択、検証後の確認、単一通常ファイルの展開のため、標準 `.update()` の代わりに明示的な処理順序を実装した。`verifying_keys` を設定して標準更新を呼ぶ設計とは異なり、空でないことを検査した埋め込み鍵を `verify_signature` に必ず渡す。
- GitHub バックエンドがタグ先頭の `v` をすべて除去することも確認した。そのため `Download` で元の `tag_name` を取得し、一つだけ除去する規則で検査してから `self_update::Release` を構築する。
- 正規名 `vss_<version>_<target>.tar.gz` / `.zip` を組み立てて完全一致で選択し、その名前を署名 context に使う。古い版への更新を拒否し、`--yes` は確認だけを省略する。
- 空の鍵集合、署名異常、SHA-256 異常では展開前に拒否する。検証済みでも通常の `vss` / `vss.exe` 以外、リンク、不正なパス、追加エントリは置換前に拒否する。
- テスト専用の固定シードで tar.gz / ZIP の署名を作り、正常更新、拒否時の既存ファイル保持、別鍵、空集合、改ざん、署名 context の版と対象の不一致、チェックサム異常、確認拒否、二重署名と信頼鍵の移行をテストした。テストでは実行中バイナリを置換せず、同じ処理の置換コールバックで一時ファイルを更新する。
- `cargo test --all --locked`、`cargo clippy --all-targets --all-features --locked -- -D warnings`、`cargo fmt --all -- --check` がローカルの macOS aarch64 で成功した。`cargo-audit 0.22.2` の検査は脆弱性の報告なし、`proc-macro-error 1.0.4` の既存の未保守警告（RUSTSEC-2024-0370）1 件で終了コード 0 だった。
- macOS と Windows の既存 CI ジョブに署名更新の単体テストと CLI テストを追加した。GitHub 上での結果は別途確認が必要である。
- 0055 と 0056 のインターフェースを `docs/signed-updates.md` に記載した。この段ではワークフローとインストーラーのアセット名を変更していないため、新名への配布側の移行は未実装である。
