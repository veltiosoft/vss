# 署名付き自己更新の配布仕様と導入条件

## 現在の状態

この実装は準備段階であり、本番の署名付き自己更新は利用できない。
本番公開鍵が未決定なので、`src/subcommand_self/update.rs` の `TRUSTED_KEYS` は空のままにしている。
この状態の `vss self update --yes` は、ネットワークへの接続前にエラーで終了する。
署名なしへのフォールバック、外部からの信頼鍵の上書き、検証を無効にするフラグはない。
テストで使用する固定シードの鍵はテスト専用で、本番の信頼鍵として採用していない。

管理者は、公開鍵、秘密鍵の管理者と保管先、署名を許可するソースと承認条件を決定する必要がある。
この文書は Secret 名、Environment 名、承認者や権限設定を決定するものではない。
決定後に公開鍵だけをソースへ埋め込み、署名付き配布と初回導入を検証するまでは、この実装をリリース可能と扱わない。

## 自己更新クライアントの検証順序

1. 引数を検査し、非対話実行では `--yes` を要求する。信頼済み鍵が空なら通信前に拒否する。
2. `self_update::Download` で GitHub API から `veltiosoft/vss` の latest Release を一度取得する。互換 major 内へのフォールバックは行わない。
3. バージョンを検査し、現在より古い版を拒否する。同一の版は更新しない。
4. 選択した版と実行環境から組み立てた名前に完全一致するアーカイブと `.sha256` をそれぞれ一つだけ選択する。旧名や類似名へフォールバックしない。
5. ダウンロードした最終アーカイブの SHA-256 を必須の `.sha256` と照合する。GitHub asset digest があれば、それも照合する。
6. 埋め込み鍵の少なくとも一つによる zipsign 署名を、期待するファイル名の context で検証する。空の鍵集合を成功にする `self_update::verify_signature` の既定動作は、その前の明示的な検査で拒否する。
7. 検証後に作る一時ディレクトリへ、通常ファイルの `vss` または `vss.exe` 一つだけを取り出す。アーカイブのパスを出力先に使わず、リンク、不要ファイル、重複、階層付きパスを拒否する。
8. 現在と更新先の版、対象、成果物名、検証結果を表示し、既定では `[y/N]` で確認する。空入力、EOF、拒否では既存バイナリを変更しない。
9. 承認後だけ `self-replace` で実行中のバイナリを置換する。`--yes` は確認入力だけを省略し、同じ検証を通る。

`self_update` は維持するが、その標準 `.update()` は呼ばない。
必須チェックサムの厳密な形式、検証後の確認、単一通常ファイルだけの展開を保証するため、`Download` と `verify_signature` の API を使って上記の順序を組み立てている。
`verifying_keys` を設定して標準更新を呼ぶ方式の代わりに、空でないことを検査した埋め込み鍵の集合を `verify_signature` に必ず渡す。
また、GitHub バックエンドはタグ先頭の `v` をすべて除去するため、元の `tag_name` を取得し、一つだけ除去する規則を適用してから `self_update::Release` を構築する。
ダウンロードはメタデータ 2 MiB、アーカイブ 256 MiB、チェックサム 4 KiB、取り出す実行ファイル 256 MiB を上限とする。

## 0055 の署名発行側とのインターフェース

### バージョンと成果物名

タグは小文字の `v` を一つだけ任意で除去し、正規の SemVer 互換 CalVer `YYYY.M.MICRO` とする。
年は 1000 から 9999、月は 1 から 12 とし、セグメントをゼロ埋めしない。
SemVer の prerelease と build metadata は許可する。
アセット名では `v` を含めず、prerelease と build metadata は省略せず保持する。
比較は SemVer precedence で行い、build metadata だけの違いは新しい版と扱わない。
署名する前に、正規化したタグとビルド対象 `Cargo.toml` の完全なバージョン文字列が一致することを検査する必要がある。

| 対象 | 正規アセット名の例 | 内容 |
| --- | --- | --- |
| Linux x86_64 | `vss_2026.10.1_linux_amd64.tar.gz` | 直下の通常ファイル `vss` 一つ |
| Linux aarch64 | `vss_2026.10.1_linux_arm64.tar.gz` | 同上 |
| macOS aarch64 | `vss_2026.10.1_darwin_arm64.tar.gz` | 同上 |
| Windows x86_64 | `vss_2026.10.1_windows_amd64.zip` | 直下の通常ファイル `vss.exe` 一つ |

tar では単純な通常ファイルヘッダを使い、GNU/PAX 拡張ヘッダやディレクトリエントリを加えない。
ZIP でもリンクやディレクトリエントリを加えない。
README やライセンスをアーカイブ内へ追加すると、新しいクライアントはそのアーカイブを拒否する。

### 署名とチェックサム

署名形式は `zipsign-api 0.2.2` で検証できる、tar.gz または ZIP に埋め込まれた Ed25519ph 署名とする。
クライアントへ埋め込む公開鍵は `self_update::VerifyingKey` の 32 バイトの raw Ed25519 公開鍵であり、PEM や Base64 の文字列をそのまま設定する形式ではない。
context は、上表の**正規アセット名全体の UTF-8 バイト列**と完全一致させる。
ディレクトリ、タグの `v`、改行、NUL を context に加えない。
別バージョンや別対象向けに正しく署名されたファイルも、名前を変更するだけでは新しいクライアントを通過できない。
署名ツールのバージョンは後続ワークフローで固定し、この検証 API との相互運用をテストする必要がある。

アーカイブごとに `<正規アセット名>.sha256` を必須とする。
その内容は `sha256sum` / `shasum -a 256` の次の形式で、一つの記録だけを含める。

```text
<64 桁の SHA-256>  <正規アセット名>
```

バイナリモードの `<hash> *<name>` と CRLF も受け付ける。
裸のハッシュ、パス付きファイル名、コメント、空行、複数記録は受け付けない。
ハッシュは署名前のファイルではなく、署名後に実際に配布するファイルから計算する。

0055 では「`cargo build --locked` → アーカイブ作成 → zipsign 署名 → 最終ファイルの検証 → SHA-256 と attestation の生成 → 全対象のアップロード → 公開」の順序を実装する必要がある。
ビルドと署名を別ジョブにし、ビルドジョブへ秘密鍵を渡さない。
署名ジョブが扱うコミットと成果物の承認条件、Environment の保護、ワークフロー変更のレビュー条件は管理者が決定する。
署名失敗、対象の欠落、タグとパッケージの不一致、最終ファイルの検証失敗では Release を公開しない。
Artifact Attestations の生成は維持し、署名済みファイルを対象にする。
クライアントでの attestation 検証は今回の実装範囲に含めない。

## 0056 のインストーラーと旧版への影響

この段階では `.github/workflows/release.yaml` と両インストーラーの旧アセット名を変更していない。
現行の公開 Release に新しい正規名があることや、本番署名の存在も確認していない。
新クライアントは鍵未設定で拒否し、鍵の設定後も旧名や未署名の成果物を拒否する。

0055 でアセット名を変更する際は、0056 で `scripts/install.sh` と `scripts/install.ps1`、インストーラーのテスト、配布案内も同じ仕様へ変更する。
既定の latest と明示タグの両方で、正規化した版と正規名を対応させる必要がある。
旧版の自己更新や古いインストーラー向けに旧名の互換アセットを用意するかは未決定であり、この段階では追加しない。
用意する場合でも、新クライアントは互換名へフォールバックしない。
旧クライアントがどのファイルを選択するかは実際の旧版ごとに確認し、「旧版からも安全に自己更新できる」とは案内しない。

## 最初の署名対応版の安全な導入

署名未対応の旧バイナリには、最初の更新時の署名検証を後から強制できない。
旧版の `vss self update` や、同じ Release の未署名 `.sha256` だけを使って初回導入の真正性を保証することはできない。

管理者が鍵を決定した後、利用者は次の手順で導入する。
別経路の具体的な公開場所と連絡先は未決定なので、現時点で実施可能な本番移行手順ではない。

1. 管理者が承認した別経路で、公開鍵の完全なバイト列またはフィンガープリントと、最初の版、対象、成果物名を確認する。同じ Release ページでの再掲だけを別経路と扱わない。
2. アーカイブ、署名、最終ファイルの SHA-256 を取得し、独立に信頼を確立した検証ツールで、確認済みの鍵と正規アセット名の context を用いて署名を検証する。検証ツールを未検証の同じ Release から取得して実行しない。
3. `.sha256` を照合し、必要な実行ファイルだけを安全に取り出して導入する。別経路で配布された最終ハッシュもある場合は、そのハッシュとも照合する。
4. バージョンを確認し、署名対応版から次の署名対応版への更新をテストする。

署名ツールを信頼して導入できない場合は、別経路で確認した正確なコミットからのソースビルドも選択肢になる。
その場合も、ビルド用ツールチェーンと依存関係の信頼は別途必要になる。
署名未対応の旧版からの自動更新だけを、安全な初回移行の代わりにはしない。

## 鍵更新と漏えい時の対応

通常の鍵更新では、まず旧鍵と新鍵の二重署名で成果物を配布し、新旧公開鍵を埋め込んだクライアントへ移行する。
移行期間を設け、旧鍵だけのクライアントと新鍵だけのクライアントで両アーカイブ形式を検証する。
その後の版で旧公開鍵を信頼集合から取り除き、署名側も新鍵だけに移す。
移行期間と旧鍵の廃棄方法は管理者が決定する。
テストでは二重署名、新旧いずれかの信頼鍵による受理、旧鍵を除去した後の旧鍵単独署名の拒否を確認する。

旧鍵が漏えいした場合は、その鍵を信頼する旧クライアントから自動的に信頼を取り消せるとは想定しない。
管理者は署名と公開を停止し、侵害範囲を調査した上で、新しい信頼鍵と復旧用成果物を独立した経路で確認できるようにする必要がある。
利用者はその確認を経て再導入する。
旧鍵で新鍵だけを承認する更新を配布しても、攻撃者が旧鍵で対抗できるため、それだけで復旧を保証しない。
管理者、Secret 名、保管先、バックアップ、通常更新と漏えい時の責任者は未決定のままであり、決定内容をこの文書へ追記する必要がある。

## 未完了の検証

ローカルの署名テストは公開されたテスト専用シードで作る tar.gz と ZIP を使い、実行中の VSS 自体は更新しない。
本番鍵による配布、GitHub での署名ジョブと保護設定、実 Release での更新は未検証である。
Linux、macOS、Windows の実行中バイナリの置換、旧版クライアント、両インストーラーとの実配布互換性も完了していない。
署名とファイル名の結び付けは実装するが、TUF 相当の失効、更新情報の鮮度保証、すべての巻き戻し攻撃への対策は提供しない。
